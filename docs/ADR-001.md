# ADR-001: Supabase and database-enforced privacy

- **Status:** Accepted for the prototype architecture
- **Date:** 2026-10-30

## Decision

Use React + TypeScript + Vite for the browser, Supabase Auth/Postgres/Storage/Realtime for app state, and one small FastAPI service for GitHub README summaries and Aadhaar encryption. Access to locked details is enforced in Postgres RLS and RPCs, not by hiding controls in React.

## Reasons

- Supabase shortens time to a credible demo while keeping identity and relational data in one managed service.
- RLS applies the same policy to browser queries and API queries, so a hidden UI cannot grant access.
- Private buckets and short-lived signed URLs limit the life of file links. A 60-second URL narrows the stale-link window; revocation is checked again on every metadata/RPC request. A storage URL already issued cannot be instantly recalled, so revocation can take effect only when that short URL expires.
- Realtime notifications make requests and revocations visible without polling.
- Aadhaar encryption happens server-side with AES-256-GCM; the key stays in API environment configuration, outside the browser and database.

## Trade-offs and revisit at scale

This design favors a small team and fewer moving parts. Before scale, add request and API rate limits, an append-only/hash-chained audit log, managed KMS and rotation, malware scanning for uploads, abuse monitoring, and a reviewed key lifecycle. Also migrate FastAPI JWT verification to Supabase JWKS for asymmetric signing and implement tenant-aware service limits.

## Trust boundaries

The browser is untrusted. Supabase Auth provides identity; RLS decides row access. FastAPI accepts an authenticated access token and handles secrets. Storage is private; signed URLs are narrowly scoped. No frontend code receives a service-role key, Claude key, or encryption key.
